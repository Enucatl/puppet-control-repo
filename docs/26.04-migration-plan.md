# OpenVox and Ubuntu 26.04 migration

[Roadmap #9](https://github.com/Enucatl/puppet-control-repo/issues/9) tracks
execution and dependencies. This document records the agreed sequence and
rebuild requirements; it does not claim that the migration has been performed.

The #12 deployment decision is a **fresh ML-DSA-44 Vault-held root hierarchy**,
with separate OpenVox and online Vault/FreeIPA intermediates. The accepted
OpenVox 18001 image and native packages precede #13's explicit new-chain
enrollment. The root key stays in Vault, which remains available for automatic
CRL rebuilding; there is no routine signing ceremony. Importing the old RSA CA into the container is not an intermediate
step. Later Atlas recovery preserves the established **new** hierarchy.
Use the [container plan](openvox-container-migration-plan.md),
[infra setup](openvox-infra.md) and [offline-root runbook](openvox-offline-root.md).
The [rehearsal report](openvox-rehearsal-report.md) distinguishes implemented
checks from remaining readiness gates. Vault's classical-only TLS fallback is
an accepted temporary exception; capable clients must negotiate ML-KEM.

## First task and migration order

Start with [#10](https://github.com/Enucatl/puppet-control-repo/issues/10): a
read-only inventory of every managed node, workload, unique-data location,
identity, bootstrap dependency, and available staging capacity. Record what
must be transferred, recreated from Git, or explicitly discarded. Record secret
locations and recovery access, never secret values in the repository or issues.

1. Prove backup coverage and restores (#11), and validate OpenVox 9 packages,
   modules, enrollment, provisioning, and CI (#12).
2. Migrate the existing configuration server on `docker.home.arpa` and all
   managed agents to OpenVox (#13), including nodes outside the Ubuntu rebuilds.
3. Rehearse and complete CA-less FreeIPA on the existing infrastructure (#14,
   #8), preserving accounts, passwords, numeric IDs, policies, and required access.
4. Rebuild the Ubuntu guests in the order below, using separate 26.04 templates
   and verified unused VM IDs (#15). Template and disposable-guest preparation
   can proceed alongside FreeIPA work; production replacements wait for #8.

| Existing guest | Replacement | Hypervisor | Cutover |
| --- | --- | --- | --- |
| `docker.home.arpa` | `atlas.home.arpa` | `proxmox.home.arpa` | #18 rehearsal, #19 first |
| `forbearance.home.arpa` | `aperture.home.arpa` | `proxmox.home.arpa` | #16, second |
| `complex.home.arpa` | `cognition.home.arpa` | `proxmox-cortex.home.arpa` | #17, third |

## Which infrastructure comes up first?

Bring up Atlas first, so migration and recovery use the same infrastructure-first
sequence. OpenVox and CA-less FreeIPA are migrated on the existing Docker host
before the Ubuntu rebuilds. That host remains authoritative during the isolated
Atlas rehearsal (#18). Staging must not run duplicate production authorities or
writers. Cut over Atlas only after its restore, acceptance and rollback checks
pass (#19); then build aperture and cognition against the active Atlas server.
The existing forbearance and complex guests must also work against Atlas before
their replacements are provisioned.

This deliberately moves the highest-impact host first. The isolated rehearsal
and independently usable recovery material are therefore prerequisites, not
checks deferred until the smaller guests have moved.

At Atlas cutover, restore the existing OpenVox server/CA state and migrate agent
server endpoints, provisioning defaults, DNS and certificate names through a
tested transition. Verify both previously enrolled agents and new enrollment.
Preserving the CA alone does not update a client's `server` setting or prove
that the replacement server's TLS name is valid. Record any temporary alias and
its retirement condition. Preserve `hcv.home.arpa`, `freeipa.home.arpa`, and the
`HOME.ARPA` realm; application URLs move to `*.atlas.home.arpa`.

For recovery with the old Docker host unavailable, use the same order:
restore the infrastructure host first, then enroll or recover dependent guests.
The recovery entry point must install the base OS, Docker, OpenVox Server and
required deployment tooling without asking the unavailable Vault or server to
enroll itself. Restore authorities and secrets from independently accessible
backups, bring services up in the rehearsed dependency order, and only then
enable normal configuration convergence and workload provisioning.

Fresh installation and restoration must share base provisioning and configuration
code. Their state-handling steps differ: a fresh installation initializes new
Vault/FreeIPA/CA identities; migration and recovery restore existing identities.
Exercise both paths in isolation before claiming the bootstrap is reproducible.

## Reproducibility acceptance

Starting from a documented Proxmox baseline, the repository must provide a
repeatable path from template creation through desktop/Docker guest provisioning,
enrollment, convergence, and required state restoration. A human may invoke a
script or supply a secret; no step may depend on an undocumented host edit.

- #10 records prerequisites, manual configuration, state locations and bootstrap
  cycles in per-host manifests, with an owner and implementation issue for gaps.
- #12 captures OpenVox server installation, Java/gems, configuration, r10k,
  hooks, ENC and autosigning in version-controlled setup, not just an installed
  server assumption. Verify supported packages for each OS/architecture; record
  tested versions and sources. No Puppet Labs package-availability gate remains.
- #15 supplies exact commands, inputs and prerequisite setup for template,
  desktop and Docker provisioning. All three paths must reject occupied IDs
  before mutation, preserve template 9000, and support the selected hostnames.
  Record image provenance/checksums and tested dependency versions so cache age
  cannot silently select a different baseline. This is reproducible functional
  configuration, not a promise of bit-identical disks.
- #18 supplies and exercises central-host bootstrap/recovery without live access
  to the old host's Vault, FreeIPA, configuration server, Git source or APT cache.
  Declare the independent Proxmox, network/DNS, package, repository, backup and
  credential access needed to start. Restore state before dependent applications.
- Every required manual action has an exact command/procedure, inputs, expected
  result and validation. Any repair discovered in rehearsal is incorporated in
  scripts or the runbook before the corresponding issue can close.
- Disposable desktop and Docker guests must complete cloud-init, expose QEMU
  agent and SSH, enroll, and converge through the documented path. Repeat the
  procedure with fresh unused IDs; verify occupied IDs leave existing guests
  untouched. Verify a subsequent normal agent run has no unexpected drift.

The current [provisioning runbook](../proxmox/README.md) distinguishes existing
behavior from these pending requirements. In particular, existing scripts are
not yet the independent central-host recovery entry point.

### Discovery handoff

Detailed host, disk, volume and endpoint observations are stored locally in the
gitignored `.migration-inventory/` directory. Keep secret values out of both
these reports and issues. The versioned implementation destinations are:

| Setup requirement | Existing source and inputs | Owner / implementation | Required evidence |
| --- | --- | --- | --- |
| Proxmox baseline and VM creation | `proxmox/README.md`; bridge, storage, snippets, administrator SSH key and image | Homelab operator, #15 | Disposable guest boots; occupied IDs are rejected |
| OpenVox server and deployment tools | Existing server configuration, package sources, r10k and Git hooks | Homelab operator, #12 | Repeatable installation and deployment |
| Independent Atlas base | Existing guest scripts depend on Vault and Puppet; separate base bootstrap still needed | Homelab operator, #18 | Base boots without the old host's services |
| Authority and application recovery | Private data manifest; backups, administrator access and recovery credentials | Homelab operator, #11/#18 | Isolated restore using independently accessible material |
| Dependent guest enrollment | Provisioning scripts, Vault enrollment policy, CA trust and server endpoint | Homelab operator, #15/#18 | Existing agents and a new guest work against Atlas |
| Hostname transition | Private endpoint checklist; router source, Compose configuration and identity policies | Homelab operator, #18/#19, then #16/#17 | DNS, TLS, authentication, NFS and application checks |

The current server explicitly uses
`/opt/puppetlabs/server/data/puppetserver` as its server data directory, alongside
configuration, SSL and CA state under `/etc/puppetlabs`. Preserve both; a search
for `/var/lib/puppetlabs` alone misses server state. Vault data, bootstrap and
unseal volumes on the same machine do not establish independent recovery access;
#11 must provide that before migration.

Stage replacements with distinct MACs and DHCP-assigned addresses. Record their
actual leases during #15 instead of reserving guessed static addresses during
discovery. Recheck candidate VM IDs, pool capacity and final address ownership
immediately before provisioning or cutover. Router lease inspection is an
execution check, not a prerequisite for recording this strategy.

## State, validation and rollback

The operator-confirmed container deployment root on Docker and Complex is
`/opt/docker`. Preserve each complete tree, including untracked environment files
and local changes, plus all named volumes. Container bind mounts outside that
tree remain separate sources: notably `/scratch`, user homes and Complex's
`/etc/wolf` and `/var/lib/wolf`. Preserve persistent content and recreate runtime
devices/sockets. Keep old-root recovery checkpoints for administrator state and
unmanaged configuration; do not overlay the old `/etc` onto the new OS.

Transfer every source classified as unique by the inventory: desktop homes and
credentials; Wolf configuration/pairing/game state; application databases,
volumes and bind mounts; `/scratch`; `/opt/git` and hooks; Vault recovery material;
FreeIPA and OpenVox authority state; untracked configuration and environment files.
Preserve ownership, ACLs, xattrs and Docker namespace mappings. Recreate caches
only where explicitly classified as disposable.

Validate OS/cloud-init, access, OpenVox enrollment and convergence, restored data,
FreeIPA/Kerberos/NFS, deployment hooks, backups and observability on applicable
hosts. Desktop acceptance covers actual user workflows. GPU hosts additionally
need proven NVIDIA driver/kernel/container compatibility, Wolf and vLLM checks.
Recheck package availability during #12/#15 instead of using historical driver
or repository observations as current facts.

Allow a full maintenance day for major cutovers. Rehearse final sync, write freeze
and rollback including data written after cutover. Keep old guests stopped for
at least 14 days and one successful weekly backup cycle, whichever is longer;
protect recovery checkpoints from pruning. Retire old identities and aliases
only after #20's acceptance. Do not run competing authorities or shared-storage
writers during staging or rollback.

## Final improvements phase

After core migration acceptance and retirement (#20), collect worthwhile cleanup
discovered during the rebuilds under
[#21: Post-migration improvements](https://github.com/Enucatl/puppet-control-repo/issues/21).
Each sub-issue should state the observed problem, smallest useful change and
validation. The first is
[#22: routine Cortex backups](https://github.com/Enucatl/puppet-control-repo/issues/22).
Check existing orchestration before introducing a second scheduler.

These improvements follow the migration rather than blocking its acceptance.
Required recovery copies of unique data, restore evidence and reproducible
provisioning remain part of the existing migration gates; deferring routine
backup automation does not defer those requirements. Keep sensitive inventory
and raw reports in the local gitignored inventory directory.
